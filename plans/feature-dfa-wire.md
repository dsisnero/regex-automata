## Dense wire contract and representation notes

Rust `src/dfa/dense.rs::{from_bytes,from_bytes_unchecked,write_to}` maps to
Crystal `src/regex/automata/dense_wire.cr`. The native v2 label, endian marker,
version, unused word, three semantic flag bits, transition/start/match tables,
special ranges, accelerator words, and quit-byte bitsets follow the pin.
The former Crystal `CRDFA001` payload is superseded. Like Rust, decoding accepts
native endian only, verifies alignment after initial padding, and reports the
consumed prefix even if trailing bytes follow. `to_bytes_*` returns
`{bytes, alignment_padding}`; `write_to_*` returns the byte count.

- **Owned decode:** Rust borrows aligned `u32` slices from the input. Crystal
  retains owned `Array(StateID)` storage plus its existing materialized
  `DFA::State` graph, since its APIs expose these mutable objects and it has no
  borrow lifetime parameter. Copying and materialization are proportional to
  input size and occur at construction. Searches use the existing flat table;
  there is no additional per-byte branch or lookup. `from_bytes_unchecked`
  deliberately uses the safe owned decoder, so it also validates in linear
  time rather than promising Rust's unsafe constant-time view.
- **Unused storage:** Rust ignores stride padding during validation but keeps
  its arbitrary u32 bits when writing again. Crystal stores nonzero unused
  words separately as UInt32 values, keeping them outside checked StateIDs.
  Accelerator padding and unused accelerator records are also retained in
  owned raw storage. These extra objects are construction/serialization-only;
  search still reads only the existing transition and accelerator tables.
- **Count bounds:** Rust's native readers decode counts through usize, while
  Crystal array/slice lengths and public count queries use Int32. Native
  metadata counts above Int32::MAX are rejected with DeserializeError before
  allocation. Such counts exceed the pinned valid PatternID domain or
  realizable Crystal buffers; this is a necessary malformed-input boundary
  difference in `dense_wire.cr::WireReader#count` and the owned component
  readers, with only construction-time checks.
- **Quit-byte decoding at this pin:** Rust
  `src/util/alphabet.rs::ByteSet::from_bytes` reads both u128 buckets from the
  same low-bucket slice. The native Crystal decoder deliberately does the
  same, including the resulting look-behind quit behavior. The standalone
  Crystal ByteSet helper is a portable literal-byte decoder; native decoding
  normalizes its input explicitly to preserve the pinned Rust result. Rust's
  own decode/re-encode changes the high bucket of the generated fixtures.
  Tests and the oracle check that result rather than asserting a raw byte copy.
- **Clone semantics:** Rust `DFA::to_owned` copies tables without deserializing
  them. Crystal `dfa.cr::DFA#to_owned` now does likewise; sparse conversion's
  existing dense-backed implementation uses that clone instead of a wire
  round trip. Starts, match slices, quit bytes, accelerators and transitions
  are independent; the immutable prefilter strategy reference is shared.
  Native readers still omit prefilters, as Rust does.

These are representation/ownership differences, not speed claims. Controlled
allocation and construction-cost measurements remain phase 8 work. Phase 5a alone does not claim sparse compatibility; phase 5b
below replaces the sparse envelope and dense backing.

## Sparse packed storage and wire mapping

Rust `src/dfa/sparse.rs` maps to Crystal `src/regex/automata/sparse.cr`.
The sparse object now retains packed native bytes and a packed start-ID table;
it retains no dense DFA. `StateID` is a byte offset. State headers, inclusive
byte-class ranges, native u32 targets, the final EOI target, optional pattern
IDs, and accelerator bytes follow Rust's layout. Conversion makes the same
two passes: determine packed offsets, then repair targets/EOI/starts/special
ranges. Dense byte classes, flags and prefilter reference are copied as Rust
does; native readers omit prefilters.

`State#next` follows Rust's linear scan over all ranges except the dummy EOI
pair. The commented-out Rust binary-search experiment is not active code.
Crystal's stack State view contains Slice values and introduces no heap
allocation per canonical Input transition. Existing Crystal Bytes convenience
searches still return their historical tuple/array results, using packed state
queries rather than a hidden dense automaton.

Native sparse readers accept unaligned buffers, require native endian, and do
not skip initial label padding. Writers support LE/BE/native output. Unlike
dense `to_bytes_*`, Rust's sparse methods return only a byte vector; Crystal
now returns `Bytes`, not the old tuple. The `CRSFA001` dense envelope and its
`.dense` inspection shortcut are superseded. Keep the original dense object
when inspecting a conversion's source is useful.

Validation walks every packed state, records actual byte boundaries, verifies
every target and materialized start against those boundaries, rejects match
starts and inconsistent match/accelerator ranges, and rejects EOI-to-quit
transitions. All seven pinned sparse fuzz payloads are replayed with the exact
Rust fuzz preamble. The offline Rust consumer also asserts rejection of those
seven files, rather than inferring it from Rust's no-panic harness alone; the
dense consumer does the same for its two files. The native low-bucket-twice
quit decoder behavior described above is preserved for sparse as well.

Representation differences and costs:

- Rust borrows sparse/start byte slices; Crystal owns copies on native decode.
  The safe `from_bytes_unchecked` alias also validates, so these operations are
  linear construction work instead of Rust's unsafe constant-time view.
- `as_ref` shares immutable packed buffers in a new Crystal class wrapper with
  independently assignable prefilter metadata. Crystal uses a heap class to
  implement the shared Automaton base; Rust returns a borrowing value struct.
  `to_owned` copies both buffers and quit metadata directly. Byte-class queries
  return a value snapshot because Crystal has no immutable-reference return
  type; transitions read the retained field directly.
- Rust alloc-backed Seen is a BTreeSet; Crystal uses Set(StateID). The source
  uses only insertion and membership, so ordering is unobservable. The standard
  Crystal set avoids introducing a separate balanced-tree dependency or object
  implementation. The allocation/lookup costs differ during validation only;
  there is no set lookup in search. Crystal requires an allocator, so the
  Rust core-only no-op Seen variant has no supported configuration here.
- Private Rust StateIter/StartStateIter/StateMut wrapper objects are inlined
  as local byte cursors and direct native writes. Dense conversion reuses the
  existing Crystal sparse-transition snapshot helper twice per state, rather
  than Rust's borrowing iterator. Those temporary arrays add construction
  allocation, with no search-time work; controlled construction-cost signoff
  remains phase 8. No throughput or allocation speed claim is made here.
- Crystal `inspect` summarizes state/pattern/payload-memory metadata instead
  of Rust Debug's full graph text. Private stack-state inspection uses Crystal
  value formatting; Debug helpers for absent private iterator/mutable wrapper
  types are skipped. These language-level inspection differences are off the
  search path.

Rust `memory_usage` counts packed transitions plus start-ID payload bytes,
excluding fixed object/header overhead. Crystal now reports that same value.
The pinned generated forward/reverse fixtures report **2,820 / 1,264 bytes**
in both implementations. `scripts/check_sparse_wire.sh` compares 15 dense
conversions and two native sparse fixtures against the pinned Rust crate,
including exact LE/BE bytes, memory, and search results. Eight construction
configurations cover byte classes, minimization and acceleration; the Crystal
matrix also checks all 256 byte targets, EOI, starts, match IDs and accelerators.

## Regex wrapper source review (5c)

Rust `src/dfa/regex.rs` maps to `src/regex/automata/dfa_regex.cr`.
The review covers all 24 inventoried methods plus private search control,
derived cloning, builder configuration and iterator behavior. The new
`spec/dfa_regex_contract_spec.cr` characterizes source contracts alongside
existing wrapper and vendor tests. Failures were observed before the fixes:
one-forward-call and incompatible-pair invariants, mutable builder settings,
capture suppression, original pattern counts, missing Input/config/Enumerable
APIs and missing clones. The pinned Rust doctests pass 15/15 offline;
`scripts/check_dfa_regex.sh` checks the additional source-derived contracts.

Search now performs one forward search, returns a miss immediately, elides
reverse search for empty/anchored matches, and otherwise runs an anchored,
non-earliest reverse search. Reverse existence, pattern equality and ordered
offsets retain Rust's explicit assertions. The parent Automaton owns UTF-8
empty-boundary skipping; the wrapper no longer duplicates it. Removing the
retry-at-each-offset miss loop removes potentially quadratic repeated scans;
this is a control-flow correction, not a measured throughput claim.

Builders mutate and return themselves for both direct configuration values
and existing block APIs. Pattern Enumerables are materialized once because
Rust receives a reusable slice. Reverse compilation disables prefilter and
specialized starts, sets anchored/All and reverses the NFA. Dense compilation
forces captures None after all user overrides. Dense flags come from the NFA,
so supporting only anchored starts does not imply inherent anchoring, and a
contradictory look can retain structural empty capability. Original NFA
pattern counts survive shadowed/impossible patterns, minimization,
acceleration, sparse conversion and native round trips. The native consumers
now cover 10 dense and 18 sparse cases, including this regression.

Remaining representation adaptations and their costs:

- Rust `Regex<A>` accepts any Automaton and defaults its component type.
  Crystal's existing non-generic Regex factory retains its closed
  `AnyDFA = DenseDFA | SparseDFA` union. Both native representations and
  supplied pairs work; custom unrelated Automaton implementations are not
  supported by this facade. Changing the public factory/getter types would
  require a separate API migration. Union dispatch occurs once per engine
  call, outside its byte loop; no new per-byte wrapper allocation is added.
- Rust borrows Input by value/reference; Crystal's `search.cr::Input` is a
  class. An unanchored nonempty match clones Input once for reverse search;
  an earliest is_match call also uses an Input clone. Miss/empty/anchored
  try_search paths no longer clone Input in the wrapper. String/Bytes calls
  allocate the existing Input object; Searcher owns its own Input snapshot.
  Clones share haystack bytes and copy range/anchor/earliest settings.
- Rust derives Clone over the component storage: owned vectors copy and
  borrowed slices share. Crystal Regex#clone always calls both to_owned
  methods for an independent owned snapshot, including for source views.
  This adds linear construction-time copy/allocation for borrowed views;
  search semantics are unchanged. Builder#clone copies config/quit metadata,
  scalar parser options and a fresh compiler; immutable seeded NFA/prefilter
  references may be shared. At regex-syntax 0.5.0's pinned parser source,
  ParserBuilder fields are scalars, so its dup isolates settings. Clone
  tests and the Rust oracle check builder isolation and both regex types.
- Derived Rust Debug uses Crystal's standard object inspection rather than
  promising identical diagnostic text. Inspection and cloning are off the
  search hot path. Phase 8 retains controlled performance signoff.
